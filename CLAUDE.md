Before starting any work, read this file, BRIEF.md, VERIFY.md, TESTS.md and PLANS.md in full.

## Rules
1. Do not change VERIFY.md; extra tests go in TESTS.md.
2. Every item in TESTS.md states which VERIFY item it comes from (`STEP1-3`); items not from VERIFY are marked "PLANS" or "補充" (supplementary) with the reason. After changing it, stop and let the user review.
3. PLANS.md may be adjusted, but must not add features BRIEF does not ask for or violate BRIEF's constraints.
4. Work through the STEPs of PLANS.md continuously: once a STEP's tests all pass, progress is recorded and it is committed, go straight on to the next one without asking. Stop for the user only in these cases: a business rule under "我先暫定的" (provisional business rules) needs to be added or changed (implementation choices under "我自己定的" (implementation choices) do not require stopping; write them into PLANS and continue); TESTS.md needs to change; stuck (a test cannot be made to pass, or the test seems wrong, see rule 6); a whole batch is finished ("第 N 批" (Batch N) in PLANS; if there are no batches, all STEPs). When stopping, hand over the review list so far (rule 9 (5)) as well.
5. Each STEP uses TDD: write the tests per TESTS.md (names start with `STEPx-y`) → run once to confirm they fail → record in progress → write the code → run **all** tests until they pass → record in progress → tick it off in PLANS.md → `git commit` once, with the STEP name in the message (e.g. `STEP 1 Read Excel: all tests pass`). After the commit do the STEP check, and only then move to the next STEP: (a) mutation testing: pick 3–5 places in the decision or calculation logic this STEP added or changed, add each as one entry to `mutations.json` and run them with `.venv/bin/python check_mutations.py <id> …` (it changes one place at a time, runs the listed tests and restores the file); anything not caught is written up as an issue and a test is added; (b) dispatch a read-only subagent (reads only, changes nothing; model opus) to review this STEP's diff against BRIEF and this STEP's VERIFY items, looking for things that should have been blocked but were not, things silently skipped, and differences from VERIFY, and write them up as issues. Fix the issues per rule 10, each with its own commit, before the next STEP; there is no need to stop for these issues unless one of the cases in rule 4 applies.
6. Do not modify tests in order to make them pass. If a test seems wrong, stop and ask first.
7. Git: `.gitignore` excludes `output/` and `.env`. One commit when a STEP is done, and one commit per later fix; do not commit unless all tests pass. Do not push or rewrite history unless the user says so. Keep writing progress.md: it records "why", git records "what changed".
8. Branches: one branch per batch of STEPs (a worktree opened by the app is one branch), started from the latest main. When a whole batch is finished, first merge main in and run all tests, and write "可以合併" (ready to merge) in the stop report. When the user says so, merge into main, delete the branch and remove the worktree; the next batch starts a new branch from the merged main, and branches do not span batches. **Nothing counts as done until it is merged into main.** If something else comes up half-way through a batch (a new feature, something not in BRIEF), do not add it to this branch: record it under "之後再做" (Later) in progress.md and open a new batch after this one is merged.
9. Batch gate: after the whole batch is done and before reporting "可以合併", do five things in order: (1) merge the latest main in and run all tests; (2) mutation testing with `check_mutations.py`: only cover logic shared across STEPs, and do not redo what the STEP checks already did; (3) dispatch a read-only subagent (reads only, changes nothing; model opus) to review the whole batch's diff against BRIEF and VERIFY, looking for out-of-scope changes, rules not approved by the user (and items in the "我自己定的" table that actually change the output), code or tests that cannot be traced back to VERIFY, and inconsistencies between STEPs; details already reviewed in the STEP checks are not re-reviewed; (4) live smoke run: first rename this case's old output in `output/` (do not delete it), open a clean session and type `/npi` following the "live-run script" in TESTS.md, sending the engineer's lines one by one as scripted. For each step record what the manager replied, the result of `status` at that moment and the files produced, and afterwards run `check_quality.py output`. The evidence is files and command output, not narration. After the evidence is recorded, rename the live-run output to `<NPI number>_smoke_<date>` and rename the old output and `output/registry.json` back, so that output approved without reading is never used as a later run's previous revision. Scope: all stations of Kalvara A0, plus the stations changed in this batch; Corvane is only run in batches where PLANS has a re-exam STEP. (5) review list: from "for the user to review" in TESTS.md pick the documents changed in this batch and hand them to the user with the paths of the live-run output. The user answers each item with "看過" (seen), "有問題" (problem) or "延後（原因）" (deferred, with a reason); open an issue for each problem; items deferred from the previous batch go first. Do not merge until every item on the list has an answer.
10. Issues: problems are recorded under "Issues" in progress.md with 5 columns: where / what was done / what should happen / what actually happened / evidence. Before fixing, add a test that fails, and write "Fixes #N" in the commit message. Do not merge while issues remain open.
11. Corrections: when the user or a review corrects a mistake that is not an issue (by Claude or by a station agent), add a date to its row under "Corrections" in progress.md, or a new row the first time. From the second date the row's "Became which check" must name, in backticks, a test function (`test_…`) or the check file that carries the rule (e.g. `ruff.toml`, `check_architecture.py`), and it must exist; or start with `文字規則：`, name in backticks the file where the rule is written, and say why it cannot be a check. Prefer a structural change (where files live, what a module may import) over one more line of instructions. Pre-commit (`check_corrections.py`) blocks the commit otherwise.

## How to run
- Environment: `/opt/homebrew/bin/python3.11 -m venv .venv && .venv/bin/pip install -r requirements.txt`
- Tests: `.venv/bin/pytest`
- Quality scorecard: `.venv/bin/python check_quality.py` (about 10 seconds). It regenerates the two cases from the test fixtures, measures them against content-depth spec §9 and prints a table; it only reports and does not block commits. To measure existing output, add a folder, e.g. `check_quality.py output`.
- Mutation testing: `.venv/bin/python check_mutations.py [id …]` (no id = all in `mutations.json`); prints caught / not caught per mutation and leaves every file as it was.
- Correction log: `.venv/bin/python check_corrections.py` (also run by pre-commit).
- Running: in Claude Code type `/npi <path to customer document>` (the manager), or `/npi status <NPI number>` to continue. The underlying commands are `.venv/bin/python -m npi intake|status|prepare|render|approve|reopen|decide ...`, and output goes to `output/<NPI number>/<revision>/<station>/`. The tool sends no email and writes to no external system, so there is no `--dry-run`.

## Report when stopping
Which STEPs were done this time (each one's commit) / test results (for each STEP: failed first, then passed, how many tests each) / whether it can be merged (result of all tests after merging main in) / results of mutation testing and the read-only review, and which issues were opened / the quality scorecard table (`check_quality.py`; which cells changed compared with the previous batch) / the result of the live smoke run and the review list (including items deferred from the previous batch) / things the user must decide / what changed in TESTS.md and PLANS.md / problems encountered
