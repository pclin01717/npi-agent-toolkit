# Project overview
When an NPI engineer receives a customer document (draft spec, ECR, PO), they hand it to the manager agent. The manager decides which stations to run and dispatches the station agents in order to produce drafts of our (LPC) documents; after each station produces its output, it stops and waits for the engineer's review, and only reviewed output is passed to the next station.

## Features to build (Batch 1: the full A0–C1 flow, every station rough first)
- **Manager agent**: recognises which case, which revision and which kind of customer document was received, decides which stations to run and dispatches them in order; stops for review after each station and records each station's status (`未跑` not run / `待審` pending review / `已審` reviewed).
- **Station agents and outputs**:

  | Station | When it runs | What it reads | Output (draft) |
  | --- | --- | --- | --- |
  | DFM / change impact | On receiving the A0 draft spec, or an ECR from B0 onwards | Customer document, factory master data, our documents from the previous revision | A0: DFM reply email (.eml); B0 onwards: change-impact assessment email (.eml) |
  | Engineering release | Previous station reviewed, and the engineer has stated the customer's decision | Reviewed email, customer decision, our documents from the previous revision | Formal spec (docx), BOM (xlsx), drawing (PDF), STEP (block, assembly) |
  | Costing | Engineering release reviewed | BOM, price list | Unit cost (xlsx) |
  | PO check | On receiving the customer PO | PO, formal spec, unit cost | PO check result |
  | Supply chain | PO check reviewed (C1 has no PO: runs once engineering release is reviewed) | PO, BOM, material master | A0: material-preparation notice email; B0 onwards: material-change notice email |

- **Every station stops for review**: the engineer can edit the draft directly, or say `可以` ("OK"); the next station reads the reviewed version.
- **What "rough" means**: it can read the inputs, write output in the correct format, and hand over to the next station. The judgement content may be incomplete, but **no invented numbers**: every amount, number of weeks, dimension and capability value must be traceable to a source; anything that cannot be traced is written as `待工程師填寫` ("to be filled in by the engineer").
- **Hand-over format**: each station's structured result is saved to a file and the next station reads from the file; when this is later moved to the Claude Agent SDK, the stations' inputs and outputs do not need to change.

## Features to build (Batch 2: non-fibre-array products such as fan-out) (added by AI)
When Batch 1 was merged the scope was set to fibre arrays; the STEP 7 exam found that the engineering-release station could only do fibre arrays (issue #18), and Corvane (36-fibre fan-out) got stuck at A0 engineering release.
- **Produce engineering-release documents by product type**: fibre arrays as in Batch 1; for fan-out (an MPO trunk breaking out into multiple single-fibre legs) the key parameters become: fibre count, trunk connector type and quantity, leg connector type and quantity, trunk length and tolerance (may be asymmetric, e.g. +50 / 0 mm), leg length and tolerance, breakout-box outline, trunk and leg cable diameters, end face (APC / PC).
- **Formal spec, BOM, drawing and STEP are all generated by type**: the finished-product name and the names of the first-level BOM assemblies are no longer hard-coded as "Fibre array"; the fan-out drawing shows the trunk, breakout box, legs and port map, and the STEP models the breakout box.
- **The product type is judged by the engineering-release agent, citing the customer document**; if it cannot be recognised or is a third kind of product, stop with an error rather than forcing it into fibre array or fan-out.
- **Corvane re-exam**: when done, Corvane runs from A0 to C1 (VERIFY STEP 7).

## Features to build (Batch 3: common items + cost sheet + BOM) (added by AI, confirmed by the user on 2026-11-01)
In STEP7-2 the user judged the quality of the Corvane output unacceptable (progress entries 36, 37): Batches 1 and 2 only verified "output exists, numbers have sources" and never defined content depth. The acceptance standard now uses `~/Desktop/FAU_Document/內容深度規格.md` (the content-depth spec; rewritten into VERIFY, not placed in the repo), and company rules use `input/00_Factory_Master_Data/LPC作業規則.md` (the LPC operating rules). Batch 3 only does the common items, the BOM and the unit cost sheet; formal spec + drawing are left for Batch 4, emails + material preparation for Batch 5 (decided by the user on 2026-11-01, progress entry 38).
- **Common 1: document dates come from event dates**. Each revision has a timeline listing LPC's own events (initial revision: DFM reply date, spec release date, cost-to-finance date, material-preparation notice date; ECR revisions: impact assessment date, spec release date, cost-to-finance date, material-preparation notice date). The date on every output comes from the timeline, not from the day it is run. Every date has a basis (a date on the customer document, the working days in operating rules §2, or a date given by the engineer). How dates are derived: see 3-1; which outputs they apply to: see 3-3.
- **Common 2: number registry**. A registry of numbers already in use (LPC product part numbers, LPC purchase order numbers, quotation numbers), checked before a new number is generated. This batch only generates finished-product part numbers: the suffix letter changes with every revision, minor changes included (operating rules §7); re-running the same revision gets the same number and does not consume another one. Purchase order numbers and quotation numbers are only registered when visible in the master data or customer documents, and only those dated no later than that revision count (so that A0 does not see numbers that only appear at B0).
- **Common 3: the operating rules can be cited as a source**. When citing a rate, ratio or number of days from the operating rules, the citation must point to a single value (e.g. FPR in the §3 work-station rates, "扇出線" (fan-out cable) in the §3 scrap rates); as with the lessons from issues #17 and #20, citing the whole document is not allowed, nor is pointing to just a row (one row of the §3 rate table holds two work stations). For values written as a range (e.g. cost lot size 500–1,500, set-up time 10–30 minutes), the chosen value and its basis are written on the document.
- **Common 4: revision kind**. For each revision, decide whether it is the initial revision, a major change (re-quote, PO revised) or a minor change (no re-quote, PO not revised); the agent judges this by citing the customer document (e.g. the ECR says "no price change requested and no PO revision"). The cost sheet's Delta is presented according to the revision kind.
- **Common 5: pending list**. After each station produces its output, the manager lists every `待工程師填寫` item of that station (which document, which cell), and the engineer fills them in from the list during review (content-depth spec §0).
- **BOM per content-depth spec §5**: 4 worksheets for the initial revision (BOM, channel map, routing, revision), and later revisions add "change summary" for 5 in total. The BOM has levels, categories (make, raw material, purchased part, packaging, consumable) and remarks mapped to operations; the routing sequences operations by product type per operating rules §4 (the extra operations for PM fibre and coating also follow §4).
- **Unit cost sheet per content-depth spec §6 and operating rules §3**: 7 worksheets for the initial revision (Summary, Parameters, Material, Services, Conversion, Rates, Approval), and later revisions add "Delta vs previous revision" for 8 in total; everything is linked with Excel formulas, recalculation gives 0 errors even when pending cells are left empty, and the total equals the value computed by the program. Summary is calculated through to the quote (cost ÷ (1 − target margin), rounded) and compared with the customer's target price; NRE is listed item by item, and ECR revisions list ECR NRE separately.
- **Templates**: the layout of the BOM and cost sheet is made into template files following the Kalvara (097) reference documents (operating rules §8), with data and layout separated.
- **Re-exam**: when done, both Kalvara and Corvane are re-run from A0 to C1 (VERIFY STEP 12).

## Constraints
- **Technology**: each agent is written as a Claude Code subagent. Python handles reading files, look-ups, calculation, filling templates, and generating PDF and STEP; judgement that requires understanding text is given to the subagents. No paid API calls.
- **Data**: `input/` is read-only and output is written only to `output/`. The data is synthetic test data.
